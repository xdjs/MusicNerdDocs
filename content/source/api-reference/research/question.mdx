### Broader follow-ups and recoverable assessment errors

Clients can provide `excludeSourceUrls` (at most 10 distinct HTTP(S) URLs, each at most 2,000 characters) when a listener asks for other activity. These are exact public citation URLs already discussed, not private conversation or instructions. Exclusions are part of the request identity and apply before saved-evidence selection; they do not authorize new providers or bypass source/date constraints. A broader recent-activity follow-up uses `retrieval: "latest"` without anchoring itself to the previous single original.

If a saved-evidence assessment returns an invalid structured model response, the durable worker allows one additional assessment on a later slice, rereading current originals. The retry is recorded and counted: saved-only work permits at most two model calls, ordinary work at most three. It does not search or scrape as part of the retry. Network failures, timeouts and unknown execution outcomes are not automatically retried. A second invalid result remains a failed operation, not a finding that evidence does not exist.

### Candidate answers and same-job continuation

The API owns public-source selection, bounded collection, durable job state and exact original revisions. It does not compose or return a listener-facing answer. A service caller can opt into `preferDirectEvidence: true` to receive bounded saved-source candidates first; `selection: "candidates"` means only that evidence is available for a checked answer attempt, not that it is sufficient.

Music Nerd Web's Ask About server-side HTTP adapter uses this option. It registers the question and job, rereads the current source revisions, then drafts against those originals. If the schema-valid writer result has zero sentences, the adapter treats the empty candidate answer as insufficient and continues the same job. The source rereads and revision checks have run, but the independent factual checker is not called because there are no factual sentences to check. This zero-sentence path is not an independently verified finding about the evidence or a global absence claim. It does not start a second job or reset the first job's limits.

A failed source read, stale revision, failed quote/fact check on a nonempty draft, or model/transport error withholds the answer and returns a bounded failure for retry. It does not trigger outside collection automatically. A fact-bearing limitation is itself a claim: it must be scoped to checked evidence, cite the supporting original, and pass the same source/claim checks. Process-only status text may say the system could not verify an answer yet; it must not imply absence outside the evidence checked. Arbitrary free-form `unanswered` text is not an answer. Web's private HTTP adapter is application implementation, not a published client SDK. Other API clients must provide their own answer registration, current-source reread, citation and verification behavior.

Keep requests neutral and public: preserve the listener's source, work, role, date, and exclusion constraints in `topic` and the structured fields that apply (`targetUrl`, `platform`, `fromDate`, `toDate`, and `evidenceNeed`). Do not send raw conversation history or private artist memory. An explicit validated lookup is the point at which the API may reserve outside-research allowance; candidate continuation alone does not reserve that allowance.

The planner/writer behavior applies to newly processed work. This rollout does not version-bust the request binding: an already verified answer remains reusable under its normal 24-hour answer-cache lifetime. A new question or retry that starts new work uses the updated planner/writer behavior.
